# 릴리즈 커밋과 tag 계약

`gg`는 Semantic Versioning tag `vMAJOR.MINOR.PATCH`를 쓰고 첫 release를 `v0.1.0`으로 시작한다. Tag push는 릴리즈를 시작하는 전달 신호일 뿐 공개 승인으로 충분하지 않다. 준비자는 저장소 default branch에서 변경사항을 stage하지 않은 상태로 `gg commit --allow-empty -m "release: vMAJOR.MINOR.PATCH"`를 실행해 전용 빈 릴리즈 커밋을 만들고, 이어서 `gg tag -a vMAJOR.MINOR.PATCH -m "Release vMAJOR.MINOR.PATCH"`로 그 `HEAD`에 annotated tag를 만든다. 이어서 `gg push --atomic origin HEAD:refs/heads/<default-branch> refs/tags/vMAJOR.MINOR.PATCH`를 실행해 릴리즈 커밋과 tag를 같은 원격 transaction으로 push한다. `<default-branch>`는 저장소의 현재 default branch 이름(이 저장소에서는 `main`)으로 바꾼다. `gg push` passthrough는 Git flag와 refspec을 그대로 전달하므로 `--atomic`은 원격이 둘 중 하나를 거부하면 두 ref를 모두 갱신하지 않아 partial push를 막는다. 원격이 atomic push를 지원하지 않아도 이 명령은 실패해야 하며 non-atomic fallback이나 force push는 쓰지 않는다. 이 기존 `gg commit`/`gg tag`/`gg push` 경로가 릴리즈 커밋과 tag를 실제로 만드는 재현 가능한 사용자 경로다. Workflow는 tag ref가 annotated tag object인지 확인한 뒤, tag를 peel한 커밋이 checkout한 `HEAD` 및 원격 default branch의 현재 tip과 같고 그 제목이 tag와 일치하며 parent와 tree가 같은 빈 커밋일 때만 게시를 계속한다.

현재 저장소에는 영구 버전 파일이나 release manifest가 없으며, release binary의 버전은 `BuildAndPackageRelease`가 `-ldflags -X main.version=<tag>`로 주입한다. 따라서 릴리즈 경계를 남기는 전용 커밋은 의도적인 빈 커밋이다. 릴리즈를 만들기 위해 무관한 영구 파일을 바꾸지 않는다.

같은 version을 다시 쓰거나 tag를 이동하거나 이미 공개한 Release/Release 파일을 덮어써서는 안 된다. 준비 단계는 기존 tag가 있으면 실패하고 force push를 쓰지 않는다. Release 불변성은 GitHub Immutable Releases 저장소/조직 설정이 published release에 적용하는 GitHub platform enforcement으로 보장한다. Workflow는 공개 전에 `RELEASE_ADMIN_TOKEN` secret에 저장한 read-only fine-grained PAT 또는 GitHub App token으로 `GET /repos/{owner}/{repo}/immutable-releases`를 호출한다. 이 secret의 최소 repository 권한은 `Administration: read`이며, `GITHUB_TOKEN`에는 이 권한을 부여할 수 없다. secret이 없거나 API 조회가 실패하거나 응답의 `enabled`가 정확히 `true`가 아니면 Workflow는 release를 publish하기 전에 실패한다. 실제 Release 생성은 권한 범위를 넓히지 않고 계속 `contents: write`와 `${{ github.token }}`만 사용한다. 현재 이 저장소의 설정은 `enabled=false`이므로 첫 public release 전에 repository administrator가 repository Settings의 Releases에서 **Enable release immutability**를 활성화하거나 organization policy가 이 repository에 적용되도록 해야 한다. 이 PR은 그 설정을 바꾸지 않는다. 이 설정은 이후 생성하는 release에만 적용되므로 기존 `v0.1.0`과 `v0.2.0`은 소급하여 immutable이 되지 않는다. 이들을 별도로 republish하면 게시일과 다운로드 통계 등에 위험이 있으므로 이 PR에서는 republish, delete 또는 tag/release 생성을 수행하지 않는다. 이 전제조건이 충족된 경우 GitHub는 published immutable release의 연결 Git tag 이동/삭제와 release asset 수정/삭제를 강제 차단하고 release attestation을 자동 생성한다. immutable release를 삭제한 뒤 tag 삭제는 가능하지만 같은 tag 이름은 재사용할 수 없다. Workflow는 기존 GitHub Release가 있으면 실패하고, 이미 존재하는 tag만 받는 `gh release create --verify-tag`를 `--clobber` 없이 쓴다. Release 파일 생성도 같은 archive 또는 `.sha256` 파일이 있으면 실패하여 로컬 재실행이 기존 asset을 바꾸지 않는다.

Go module path는 첫 release 전에 `github.com/dungsil-ai/gg`로 바꾼다. Release 파일과 함께 `go install github.com/dungsil-ai/gg@latest`를 지원하고 README에 두 설치 방법을 모두 적는다.

Release archive 이름은 `gg_<version>_<os>_<arch>.<ext>`로 한다. Windows는 `.zip`, Linux와 macOS는 `.tar.gz`를 쓴다. 각 archive는 같은 이름 뒤에 `.sha256`을 붙인 checksum 파일을 따로 가진다. 공통 `checksums.txt`는 만들지 않는다.

Release binary는 `gg version`과 `gg --version`에서 `gg v0.1.0`처럼 tag version을 보여준다. 일반 local build는 `gg dev`를 보여준다. `v0.x` 범위에서는 SHA-256만 제공하고 Windows code signing, macOS notarization, GPG, Sigstore는 인증서와 secret 관리 범위를 늘리므로 제외한다.

검증은 두 근거를 분리한다. Workflow 수준 검증은 로컬과 CI 테스트에서 annotated tag, 릴리즈 커밋과 default branch tip provenance, 기존 Release 부재, `RELEASE_ADMIN_TOKEN`을 사용한 Immutable Releases 설정 조회, 빌드/아카이브/체크섬 생성을 확인한다. 공개 직전 gate는 endpoint가 `enabled=true`를 반환했음을 확인하지만, 최종 Release의 `immutable=true`는 publish 뒤 GitHub platform enforcement로만 확인될 수 있다. 실제 tag push 공개 운영 gate는 전용 릴리즈 커밋 검증, 관리자 설정 활성화, `RELEASE_ADMIN_TOKEN` 제공, `verify` 성공 및 6개 OS/arch build 성공 뒤 public GitHub Release를 생성하는 것으로 확인한다.

공개 전 검토용으로 별도 유지하는 Draft release와 공통 checksum 파일은 선택하지 않았다. 다만 `gh release create`는 asset을 받으면 내부적으로 draft 생성, asset 업로드, publish를 순서로 수행하므로 이 staging은 published immutable release 전에 asset을 완성하는 전송 절차일 뿐 별도 운영 release가 아니다. 공개 가능한 정확한 tag와 불변 Release를 쓰고 각 파일 옆에서 checksum을 바로 찾을 수 있게 하기 위해 공통 checksum 파일은 만들지 않는다.
